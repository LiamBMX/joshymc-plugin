JOSHYMC PERMISSIONS
===================

Complete reference of every joshymc.* permission node, generated by auditing
plugin.yml, config/data files (kits.yml, tags.yml, config.yml), and every
hasPermission() check in the source tree. Keep this file up to date whenever
a permission is added, removed, or renamed — see the AUDIT NOTES section at
the bottom for known gaps/oddities found while compiling this.

Format: node, one-line description, command it's tied to (if any), Default.
"Default: true" = granted to everyone out of the box. "Default: OP" = only
server operators get it unless a permissions plugin (e.g. LuckPerms) grants
it explicitly to a rank. "Default: false" = nobody gets it until explicitly
granted, even OPs.

==================================================
AUDIT NOTES (mismatches found while compiling this file)
==================================================

Fixed as part of this audit (safe, additive/backward-compatible changes):

- plugin.yml had a duplicate `aliases:` key under the `killtop:` command
  entry (one listing `[killerboard, killstop]`, immediately overwritten by
  a second `[killerboard]`). YAML keeps only the last key, so the
  `killstop` alias silently never worked. Fixed by merging into a single
  `aliases: [killerboard, killstop]`.

- `joshymc.spawner.admin` (singular) was checked by SpawnerCommand.kt for
  `/spawner`'s admin subcommands, while SpawnerManager.kt checked
  `joshymc.spawners.admin` (plural) for ownership-bypass in the spawner
  storage/filter GUI — nine call sites on the plural form vs. two on the
  singular. A staff member granted only one of the two nodes would get
  inconsistent access. SpawnerCommand.kt now accepts either node, and
  `joshymc.spawners.admin` (the more heavily-used plural form) is the one
  documented and declared with a default in plugin.yml going forward.

- The following permissions were being checked with `hasPermission()`
  somewhere in the source but had no entry at all in plugin.yml's
  `permissions:` block (meaning they silently defaulted to OP-only,
  regardless of the surrounding command's intent). They've been added with
  defaults matched to the equivalent sibling permission on the same
  command family: joshymc.team, joshymc.team.admin, joshymc.bounty,
  joshymc.hopper, joshymc.hopper.upgrade, joshymc.hopper.admin,
  joshymc.shop.create, joshymc.shop.admin, joshymc.nick.noprefix,
  joshymc.nick.bypassfilter, joshymc.gadget.nocooldown,
  joshymc.chat.profanity.bypass, joshymc.anticheat.fly.bypass,
  joshymc.trail.*, joshymc.spawners.admin.

Reported, not changed (would need a design decision from Joshy — flagged
here rather than guessed at):

- joshymc.shop is declared as "Access the server shop" but is actually only
  enforced by `/chestshop`'s command class; `/shop` (the server shop GUI)
  has no permission check anywhere and is fully open to all players. The
  description in plugin.yml has been corrected to reflect what it actually
  gates; nobody's access changes as a result.

- The following permissions are declared in plugin.yml but are not checked
  anywhere in the current code, so granting or denying them currently has
  no effect: joshymc.spawn (the base `/spawn` teleport itself is open to
  everyone; only the `drops`/`containers` admin subcommands are gated, by
  joshymc.spawn.admin), joshymc.vote, joshymc.rank.list, joshymc.market.
  Left in plugin.yml rather than removed, in case they're intentionally
  reserved for a future enforcement pass — verify with Joshy before
  deleting, since removing a declared node can affect existing LuckPerms
  templates even if it currently does nothing.

Dynamic / config-driven permissions (intentionally not declared
individually in plugin.yml — see the "Dynamic per-..." notes under KITS
and COSMETICS above, and the ORDERS section for joshymc.orders.limit.<key>):
these are generated from kits.yml, tags.yml, and each cosmetic manager's
registered item list, so the exact set of valid nodes depends on what's
currently configured rather than being fixed at compile time.
